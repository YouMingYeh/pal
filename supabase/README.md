# Pal database

Apply every migration in filename order to a dedicated Supabase project. They define the group chat, RLS, atomic job queue, reminder delivery, replay handling, and explicit grants. The Cron migration enables `pg_cron` and delivers due reminders once per minute. Enable Email Auth; the application signs in with real Supabase sessions.

Authenticated clients can read only their groups' rows. Clients write through `create_group(p_name)`, `join_group(p_invite_code)`, and `send_message(p_group_id,p_body,p_client_id)`. The four-argument overload also accepts `p_reply_to_id`; a reply must belong to the same group. Invite codes are UUID bearer invitations; share them only with intended members. Reusing a message client ID is idempotent and changing its body or reply is rejected.

In v1, every human message queues passive work after ten seconds of silence; `@Pal` is immediate. URL ingestion shares the same canonical source pipeline. Invalid URLs are skipped without losing the chat message. A paused group queues no new agent work and cancels running scopes. `claim_agent_jobs` serializes each group, freezes `batch_message_ids`, and marks covered jobs `coalesced`. Pal/system card messages do not enqueue chat jobs. `complete_agent_job` accepts an empty response for a silent passive scan.

The server uses its secret key to call `claim_agent_jobs(p_limit)`, `complete_agent_job(p_job_id,p_attempt,p_body,p_result)`, and `fail_agent_job(p_job_id,p_attempt,p_error)`. Claiming leases a job for five minutes and increments its attempt. Completion checks the attempt, posts one Pal message, and completes the job atomically. Failed jobs retry up to three attempts; expired leases are recoverable. Store the Eve session ID in `agent_jobs.result` as serialized JSON. Only clear it after a terminal Eve failure; a disconnected worker should resume the existing session.

After deploying the API, store its full HTTPS `/api/dispatch` URL in Supabase Vault as `pal_dispatch_url` and the server's `CRON_SECRET` as `pal_cron_secret`. Then apply `agent-recovery.sql` to schedule a minute-by-minute authenticated HTTP dispatch. It references Vault at execution time so the bearer token is absent from migration files and the Cron job's SQL. Do not select decrypted Vault values in logs. Supabase's `net._http_response` records HTTP status; check it together with `cron.job_run_details` to verify requests reached the API.

The server's scoped reminder tool calls `create_reminder(p_group_id,p_requester_id,p_body,p_due_at,p_timezone,p_source_key)`. It checks actual membership, future time, IANA timezone, and a stable idempotency key. `private.deliver_due_reminders()` locks up to 100 due rows, posts one message per reminder, and marks them completed in the same transaction. It runs entirely in Postgres while clients and the API server are offline. In v1, message insertion also writes an APNs outbox atomically. The application integration worker sends the actual notification; database delivery alone does not prove APNs delivery.

`tests/v1.sql` is the current assertion suite for a **dedicated, empty test database**. It creates three Auth fixtures in a transaction and rolls back. Run using `psql "$PAL_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/v1.sql` after applying every migration. It covers membership isolation, member/agent authority, deduplication, batching, pause invalidation, OAuth consume, calendar leases, token refresh, source polling, reminders, push targets, and rescheduling. The older `tests/spike.sql` describes the original mention-only queue and is intentionally superseded. Supabase's direct default grants to client roles are explicitly revoked; revoking `PUBLIC` alone is insufficient. Live Cron and provider delivery still require remote verification.

Do not expose a Supabase secret or service-role key in the iOS app. Group membership must also be checked by every privileged backend route because the server key bypasses RLS.

## V1 state and actions

`pal_group_state(p_group_id)` returns `{members,places,sources,polls,plans,memories,reminders,reactions,settings}`. Authenticated members can read it; the service role can read a known group without a user JWT. Profiles use `user_id` as their primary key. Profile names are visible to shared group members; tokens, devices, OAuth states, and integration queues remain private.

`pal_profile_save(p_data)` edits only `auth.uid()` and accepts `display_name`, nullable HTTPS `avatar_url`, and `notification_preferences:{enabled:boolean}` (or the `notifications_enabled` alias). `pal_action(p_group_id,p_action,p_data)` derives the actor from Auth. `pal_agent_action(p_group_id,p_requester_id,p_action,p_data)` is service-only and still validates real group membership. Each action is serialized by the group row. An optional `source_key` returns the same recorded result on retry; reusing it with different input is rejected. Agent mutations require a source key. If supplied, `job_id` must identify a running job in the group.

| Action | Data |
| --- | --- |
| `group.settings` | Optional `name`, `timezone`, `agent_paused`, `proactive_suggestions` |
| `group.read` | `message_id`; advances monotonically to that message's timestamp |
| `message.reply` | `body`, `client_id`, `reply_to_id` |
| `reaction.toggle` | `message_id`, `emoji`; agent reactions have `actor:pal,user_id:null` |
| `memory.save` / `memory.delete` | Save: optional `id`, `kind:preference\|availability`, `key`, `value`, optional source/expiry. Delete: `id`. Own memories only. Availability requires future `expires_at`. Agent saves require a source message from that member. |
| `source.create` / `source.update` | Create: `url`, optional `title`, `source_message_id`. Update: `id`, optional `title`, `status`, `candidates`, `place_ids`. |
| `place.save` / `place.correct` / `place.delete` | Save: `name`, `address`, `latitude`, `longitude`, `provider`, optional `provider_id`, `source_id`, `website`, `booking_url`. Correct: `id` plus changed fields. Delete: `id`; places used by confirmed plans must first be removed from those plans. |
| `poll.create` / `poll.vote` | Create: `kind:place\|time`, `question`, 2–8 `options:[{id,label,place_id?,starts_at?,ends_at?}]`, future `deadline_at`. Vote: `id`, `option_ids`; actual member identity is used. |
| `plan.create` / `plan.update` | `title`, `starts_at`, optional `ends_at`, `place_id`, `notes`; update also requires `id`. New plans are drafts. Changed time/place clears old RSVPs and invalidates old reminders/calendar sync. |
| `plan.confirm` / `plan.cancel` / `plan.rsvp` / `plan.booking` | `id`; RSVP adds `status:going\|maybe\|declined`; booking adds `status:needed\|requested\|booked\|failed` and optional `reference`. These decisions are member-only. |
| `reminder.create` / `reminder.update` / `reminder.cancel` | `body`, `due_at`, `timezone`, optional `target_user_ids`, `plan_id`, `poll_id`; update/cancel require `id` and the requester. |

Resolved places require coordinates. A real provider ID deduplicates map results; native results without IDs use a deterministic coordinate/name identity. Shared sources and places retain all contributors. A place card always references the **source ID**, so partial extraction and saving multiple candidates update one card. Poll cards use `choice` or `availability` and reference the poll; other cards reference their plan/reminder. The native transcript renders these persisted records as text in the current demo; the card schema and legacy poll actions remain for compatibility. Source URL/title can be null for manually saved places. Ambiguous extracted candidates are stored without a pin.

Source canonicalization removes fragments and known tracking parameters, including Instagram `xtok`, while preserving meaningful query parameters and the original shared `sources.url`. Existing records are not merged or deleted when the normalization rules change.

Agent actions can create/edit sources, places, polls, drafts, own explicit memories and requested reminders, and react as Pal. They cannot vote, RSVP, confirm plans, book, change group settings, or impersonate another member's memory. The backend must derive source speakers from verified messages rather than a model-supplied user ID.

## Scheduled work and provider queues

The same source-scoped response RPC accepts `p_target_kind: confirmation` with only `{plan_version}` when the server independently verifies explicit human confirmation intent. It requires a future same-group draft, its current version and a source newer than its last edit. It invokes the existing member `plan.confirm` action using the source speaker; broad agent confirmation stays forbidden. Source receipts make retries safe without restoring a later cancelled plan. Confirmation creates no attendance response or personal calendar event; those still require the member's own RSVP.

Authenticated `ensure_pal_direct()` creates or reuses the caller's single private Pal chat. Direct rooms contain only their creator, reject invite joins and respond immediately without `@Pal`. Service-only `pal_read_across_groups(p_job_id,p_attempt,p_offset default 0,p_query default null)` requires a live owner-DM job and reads only the owner's current ordinary-group memberships. Pages contain at most five groups with bounded recent messages, plans, places, sources and the owner's unexpired memories; other private chats and private provider fields are excluded. Message excerpts are at most 500 characters and explicit truncation flags preserve their limits. Queries match literal group names or recent message text. The host further caps the complete tool result at 32,000 UTF-8 bytes.

Pal reply expressions use optional `messages.emotion`, restricted to the handoff's twelve keys (`fier`, `heureux`, `hilare`, `curieux`, `confus`, `surpris`, `timide`, `triste`, `colere`, `somnolent`, `attentif`, `neutre`) and Pal messages. Historical rows stay unchanged; clients fall back to `fier`. Service-only `complete_agent_job_with_emotion(p_job_id,p_attempt,p_body,p_result default null,p_emotion default 'fier')` validates a live lease and current group controls before committing the reply. The old completion RPC delegates with `fier`; silent replies remain silent and duplicate source keys preserve their first body and emotion. Authorized group state always includes `pal_activity: {activity,job_id,status,expires_at}`. Real due chat work reports `thinking`/`accepted` for at most five minutes after `run_after`; live chat leases report `thinking`/`running` until the lease expires. Otherwise it reports `idle` with null metadata. Future debounced work, weekly jobs, paused groups, exhausted retries and expired jobs cannot keep the mascot thinking. The current native chat does not display this processing state: scanning a message is not a promise that Pal will reply.

Service-only `pal_capture_member_response(p_job_id,p_job_attempt,p_source_message_id,p_evidence,p_target_kind,p_target_id,p_response)` records explicit own conversational votes or RSVPs through the existing human action path. The backend first resolves unambiguous intent; the database requires a live job lease, the frozen batch's actual human speaker, current membership and evidence equal to the entire message. Poll responses support valid options, either/all, and none for time polls. RSVPs require the current version of a confirmed future plan and a source newer than that plan's last update. Targets cannot cross groups, and callers cannot supply another actor. Source provenance and private receipts make retries safe; later manual or conversational decisions take precedence, returning `{captured:false,reason:"newer_response"}` for stale work. Ordinary manual actions clear automatic provenance. Plan confirmation, cancellation and booking retain their explicit human controls.

Named group creation with an optional photo uses service-only `pal_group_create(p_user_id,p_client_id,p_name,p_avatar_path default null,p_sha256 default null)`, returning `{group,uploaded_path_used}`. Group JPEGs stay in the same private `avatars` bucket under `groups/<creator UUID>/<random UUID>.jpg`. A private receipt freezes the initial name and input-file hash; an advisory lock and unique receipt key prevent duplicate groups on concurrent or lost-response retries. Name, avatar reference and creator membership commit together. A retry returns the current authorized group without undoing a later rename, and identifies any unused new uploaded file for cleanup. Existing `create_group(text)` remains supported. Member-only `groups` reads and group-state settings expose `avatar_path` plus `creator_id` for backend signing; outsiders cannot read them.

Photo and voice messages use private `message-attachments` storage and group-readable `message_attachments` metadata. Only the backend may access blobs or call `send_attachment(p_group_id,p_user_id,p_client_id,p_object_path,p_kind,p_mime_type,p_byte_size,p_width,p_height,p_duration_ms,p_sha256,p_body default null,p_reply_to_id default null)`. It verifies the session and validates the real file before using an owner/group-scoped `<group UUID>/<user UUID>/<random UUID>.jpg` or `.m4a` path. JPEGs have dimensions at most 1024; M4A uses `audio/mp4` and lasts at most 60 seconds. Both are limited to 4 MiB. `input_sha256` hashes the input file before normalization. The database saves the ordinary message, attachment and agent job atomically, retaining existing reply, pause and URL behavior. A matching retry returns the original `{message,attachment,uploaded_path_used}`; the backend removes a newly uploaded unused blob when that flag is false. A changed hash, kind, caption or reply, or an existing text-only message with that client ID, is rejected. Backend reads authorize current group membership before issuing expiring signed URLs.

Uploaded avatars use the private `avatars` bucket, limited to server-compressed JPEGs of at most 5 MiB. Storage access is service-only, including for members sharing a group. `pal_avatar_replace(p_user_id, p_avatar_path, p_display_name default null)` atomically saves an owner-scoped `<user UUID>/<random UUID>.jpg` reference and optional name, returning `{profile, previous_path}` for cleanup. The backend derives the user from its verified session and signs paths only after authorizing profile or group reads. Authorized member state includes `avatar_path`; the backend replaces it with a signed `avatar_url` and strips the path. Legacy URLs survive migration; replacing or explicitly clearing an avatar removes the legacy reference. A `pal_profile_save` patch containing `avatar_url: null` also clears the private path and returns transient `_previous_avatar_path` from the locked row; the backend strips this field and cleans up that old object.

Time polls accept an explicit `poll.vote` with `option_ids: []` to record “None work.” Place polls require at least one valid option; omitted options are rejected. State includes `polls[].responses: [{user_id, option_ids}]` alongside the existing flat `votes` array. An empty response is an answered decline; a missing response is unknown. Nudges target only members without a response, and all members responding cancels remaining poll nudges.

The existing minutely reminder Cron now also handles poll halfway/deadline nudges and optional weekly suggestions. `pal_maintenance()` exposes that same work to the service-only dispatcher. All responses cancel remaining poll nudges. Confirmed plans schedule 24-hour and two-hour reminders only for current `going` RSVPs. Automatic nudges wait through 22:00–09:00 in the group timezone; event reminders that would arrive after the event are cancelled. Explicit reminders still post into chat at their requested time, with quiet-time pushes delayed. Expired dated availability is excluded from state. Weekly suggestions are limited to once per seven days, Monday at 10:00 local time, and require saved places plus enabled proactive suggestions.

`pal_claim_sources(p_limit)` leases pending/resolving extraction rows. `pal_complete_source(p_id,p_result)` accepts `expected_attempt`, `status`, `provider_job_id`, `extraction`, `metadata`, `candidates`, and optional `place_ids`/validated resolved `places`. A partial `resolving` update releases its lease and retries after 30 seconds, preserving paid extraction data and the provider job ID. Terminal resolved/needs-confirmation results stop polling. `pal_fail_source` records terminal failure. The worker must validate external URLs and avoid submitting a second provider job when `provider_job_id` is already stored.

`pal_integration_state(p_kind,p_limit)` and `pal_integration_update(p_kind,p_id,p_data)` are service-only. Kinds are `oauth_states`, `google_connections`, `google_sync_items`, `push_devices`, `push_outbox`. `get`/`put` return one row; `delete` returns `{ok}`. OAuth `claim` atomically consumes an unexpired state and returns a row or null. Calendar-creation `claim` takes a five-minute connection lease. Queue `claim` returns arrays of leased rows, decorated with plan/place/group/connection for Google or devices for APNs. Queue `finish` requires `expected_attempt`; Google also requires `expected_version`.

Google `desired_version` is a monotonic **sync revision**, which may exceed the plan's version. New decisions/reconnects invalidate leases and reset attempts while advancing that revision. Stale completion returns `{ok:false}` and requeues an already-synced row to repair a possible late provider write. Calendar removal finishes `synced` with `event_id:null`. Access-token refresh uses `expected_status` and `expected_encrypted_refresh_token`; it does not invalidate sync leases or revive a disconnected connection. An explicit `resync:true` reconnect queues current confirmed plans for going members.

Private Google credentials and OAuth verifiers are encrypted by the application; the database never implements its own cipher. Connection `calendar_id` starts null and preserves the dedicated Pal calendar across reconnects unless explicitly cleared. `pal_device_register(p_token,p_environment)` and `pal_device_delete` derive the current user and never return tokens. APNs environment is `sandbox` or `production`. Push claims recheck current membership, notification preferences, reminder cancellation and RSVP status. Outbox source keys deduplicate database delivery; provider calls still require retry-safe handling by the worker.

Internal weekly scheduler messages never enter the push outbox. Actual card notifications persist their `type` and `entity_id` alongside the original APNs alert, so tapping an availability/place/plan card opens the exact entity.
